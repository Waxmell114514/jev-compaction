# Recoverable / lossless context offloading and recall for LLM agents, and the long-session benchmarks that would test it (as of 2026-10-14)

Scope note: this survey covers (a) prior systems that make dropped context *recoverable* rather than summarized, (b) agent-memory systems and their retrieval mechanisms, (c) benchmarks with long enough coding sessions to show whether recall matters, (d) how prior work evaluated retrieval of past observations, and (e) proactive / harness-side retrieval. Everything below is cited to a primary source where one was reachable; items marked **[unverified]** come only from secondary write-ups or from an abstract page that did not contain the detail. Several arXiv PDFs could not be parsed by the fetch tool, so for those I used the arXiv HTML versions; where the HTML was truncated I say so.

---

## KQ1. Prior "pointer / reference / lazy-load" designs: does any give byte-exact expand of elided tool output?

### Takeaway
Yes, several do, and the closest prior art to jevctx's `expand(pointer)` is now well documented: (1) the "Empirical Study of Harness Design for Coding Agents" (arXiv 2609.20804, Sept 2026) implements exactly an elision-stub + `recall_event(id)` tool that returns the verbatim original, and reports that recall is almost never used and adds no accuracy; (2) "Agent-Controlled Forgetting for Tool-Using Agents" (arXiv 2610.10590, Oct 2026) archives tool results byte-exactly with `context_recover(archive_ref)`; (3) OpenDev (arXiv 2603.05344) offloads outputs >8,000 chars to a scratch file leaving a 500-char preview + path; (4) Manus and SmoothAgent explicitly frame "restorable/offloaded" context (URL/path kept, content dropped) as the lossless alternative to summarization. Commercial harnesses (Claude Code, OpenHands, Letta) keep originals in a log but expose recovery mostly via re-reading files or memory files, not a dedicated byte-exact expand of the tool result itself. None of the prior systems adds a learned reranker on top of the pointer store; retrieval is by explicit ID, file path, grep, or embeddings.

### Cited Findings

**Research harness with explicit elision + verbatim recall (closest prior art)**
- "An Empirical Study of Harness Design for Coding Agents" (arXiv 2609.20804v1; authors Run-Ze Fan, Zihao Zhang, Simin Ma, Yebowen Hu, Shouju Wang, Kaiqiang Song, Fei Liu, Hamed Zamani, Xiaoyang Wang) compares five context-management tiers built from three mechanisms: elision (M1), recall of elided content via a `recall_event` tool (M2), and LLM summarization (M3). T0 = none; T1 = elision only; T2 = elision + recall; T3 = summarization only; T4 = staged (elide first, summarize only if still too large). — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- Elision design: old tool outputs are replaced with a stub reporting the removed size (line and character counts); under T1 the stub says to "Re-read or re-run"; under T2/T4 it also gives the event ID for `recall_event`. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- `recall_event` "returns the verbatim messages of a past event by ID, including full tool output"; read-only; errors on out-of-range IDs; its tool description tells the model to prefer re-running/re-reading when easy and reserve recall for hard-to-reproduce outputs such as past test logs. The running summary (T3/T4) is wrapped in `<context-summary>` with fixed headings (Goal, Files touched, Done, Pending, Errors & fixes, Current state, Next step) and notes that raw content remains recallable up to a given event ID. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- Benchmarks: SWE-Bench Verified (500 issues) and Terminal-Bench 2.1 (89 tasks); four models; 32k/64k/96k/128k context budgets; 176 settings. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- Key result on recall: "Recall is rarely used and adds no accuracy. T2 differs from T1 by only −0.36 points on average. Among T2 and T4 settings, 36 of 64 never call `recall_event`, and average use drops from 0.540 calls per task at 32k to about 0.007 at 128k." Table 13: SWE-Bench T4@32k ranges 0.006 (Nemotron-3 550B) to 0.472 (Nemotron-3 30B) calls/task; Terminal-Bench Nemotron-3 30B T2@32k = 4.326 calls/task, T4@32k = 2.708; all 16 planning/action-space ablations at T4/128k record zero calls. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- Budget sensitivity: on SWE-Bench the managed-vs-T0 gap shrinks from 35.7 to 2.7 percentage points as budget grows 32k→128k; T0 window-overflow failures fall 78.7%→8.7%; managed tiers had zero overflows. At 32k, unmanaged runs have median length 20–30 turns and mostly stop during localization; managed tiers extend medians to ~50–180 turns. T4 lowest cost in 7 of 8 panels. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)

**Agent-controlled archiving with byte-exact recovery**
- "Agent-Controlled Forgetting for Tool-Using Agents: Reversible Context Curation in Practice" (arXiv 2610.10590v1, Jan-Peter Franke, 6 Oct 2026): the acting model calls `context_apply` with (result_id, note) pairs; the harness stores each result's raw text, images and provenance in an archive and replaces the active body with a stub containing the note + archive reference; `context_recover(archive_ref)` returns the original as a new tool result with a fresh ID without re-running the tool. Paper states archived payloads match recorded tool returns exactly (byte-exact integrity reported for 26 payloads in the central pair). — [arXiv 2610.10590](https://arxiv.org/html/2610.10590v1)
- Numbers: OpenTelemetry debugging case: final prompt tokens 231,951 (method) vs 912,492 (retained) = 75% reduction; cumulative input 22.99M vs 45.77M; cost $1.28–1.44 vs $4.38; primary oracle 2/2 both arms; follow-up 3/6 vs 2/6. Planroom: 12/12 both arms, method +6% final prompt tokens. Browser continuation: method 63% fewer tokens but 4/12 vs 6/12. Sessions were 98–442 requests long. **Zero recovery uses in the central pair**; the paper says the effect of archiving on decisions and downstream retrieval is unmeasured and defines no lost-context metric. — [arXiv 2610.10590](https://arxiv.org/html/2610.10590v1)

**Offload-to-file with preview + path (OpenDev)**
- "Building Effective AI Coding Agents for the Terminal: Scaffolding, Harness, Context Engineering, and Lessons Learned" (arXiv 2603.05344v3, Nghi D. Q. Bui, "OpenDev", 13 Mar 2026), §2.3.2 Large output offloading: outputs over 8,000 characters (~2,000 tokens) are written to `~/.opendev/scratch/<session_id>/`; context keeps a 500-character preview plus a reference path with line count and total characters; recovery hint "Use read_file to see full output if needed" (or delegate to a Code Explorer subagent). Command output ≤100 chars kept verbatim; errors truncated to 200 chars; per-tool summaries 50–200 chars. — [arXiv 2603.05344](https://arxiv.org/html/2603.05344)
- §2.3.6 five-stage progressive compaction: 70% warn; 80% observation masking (older tool results replaced with ~15-token reference pointers); 85% fast pruning (`[pruned]` markers); 90% aggressive masking; 99% full compaction (history serialized to a scratch file, middle summarized, Artifact Index + archive path in summary). Claimed: ~54% reduction in peak observation context; offloading extended typical sessions from 15–20 turns to 30–40 turns without compaction. No measurement of how often offloaded output was re-read. — [arXiv 2603.05344](https://arxiv.org/html/2603.05344)

**Industrial statements of "restorable" compression**
- Manus (Yichao 'Peak' Ji, 18 Jul 2025): "we treat the file system as the ultimate context in Manus: unlimited in size, persistent by nature"; "Our compression strategies are always designed to be restorable"; "the content of a web page can be dropped from the context as long as the URL is preserved"; "a document's contents can be omitted if its path remains available in the sandbox"; warns "overly aggressive compression inevitably leads to information loss"; KV-cache hit rate called "the single most important metric". — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- SmoothAgent (arXiv 2607.00151v1, UCSD, 30 Jun 2026) formalizes three transform classes for serving: offloading ("moves observations such as tool outputs to external storage and replaces them with references ... maintains exact fidelity"), keep-recent-K, and summarization (lossy, ~128-token summaries); in their synthetic runs offloading triggers at 15K tokens, 28 steps × ~600–650 tokens, 32K max. Headline: 62% tail-TTFT reduction via lookahead KV precomputation. — [arXiv 2607.00151](https://arxiv.org/html/2607.00151)
- Anthropic "Effective context engineering for AI agents" (29 Sep 2025): just-in-time retrieval = agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and load at runtime; Claude Code's compaction "preserves architectural decisions, unresolved bugs, and implementation details" and discards "redundant tool outputs or messages"; after compaction the agent continues with the summary plus "the five most recently accessed files"; tool-result clearing is "one of the safest lightest touch forms of compaction". — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Commercial harness mechanics (what is and is not recoverable)**
- Anthropic API context editing: `clear_tool_uses_20250919` clears oldest tool results server-side when input exceeds `trigger` (default 100,000 input tokens), keeps `keep` recent pairs (default 3), optional `clear_at_least`, `exclude_tools`, `clear_tool_inputs`. The API "replaces each cleared result with placeholder text indicating to Claude that it was removed" (exact wording not published). Clearing is server-side; client retains full history. **The only documented recovery path is the memory tool**: Claude gets an automatic warning near the threshold and can write essential results to `/memories` first. Server-side compaction `compact_20260112` is the recommended summarization path. — [Claude Platform docs: context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Memory tool (`memory_20250818`): client-side file ops (view/create/str_replace/insert/delete/rename) under `/memories`; the API auto-injects "ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory." Docs describe pairing with compaction: "compaction keeps the active context small ... and memory preserves the information that must survive summarization." No eval numbers on the page. — [Claude Platform docs: memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Claude Code internals per the eleven-system source-code study (arXiv 2609.00006v1, Barbaste, Darrigol, Vu, Wiltberger, 2 Sep 2026): compaction triggers when the running token estimate enters a buffer `AUTOCOMPACT_BUFFER_TOKENS = 13 000` below the effective window; steps: strip images → group by API round → summarize → insert compact-boundary message; post-compaction restores up to 5 files within `POST_COMPACT_TOKEN_BUDGET = 50 000`. Tool-output handling "not specified beyond image stripping" in that section. — [arXiv 2609.00006](https://arxiv.org/html/2609.00006)
- Same study, other harnesses: Gemini CLI compresses at 50% of the window, keeps most recent 30% verbatim, with pluggable processors "rolling summary, node truncation, blob degradation, and tool masking" and per-file levels FULL/PARTIAL/SUMMARY/EXCLUDED; OpenCode has opt-in tool-output pruning that "soft-deletes old tool outputs", protects newest 40K tokens, fires only if >20K reclaimable, plus a shadow git repo snapshot per step; Pi keeps sessions as append-only JSONL trees where "the original history remains in the tree"; Hermes "lineage compaction" ends the SQLite session and starts a child linked by `parent_session_id`, "No history is destroyed", history indexed with SQLite FTS5; OpenHands condensation is "event-sourced, so compression history is replayable". — [arXiv 2609.00006](https://arxiv.org/html/2609.00006)
- OpenHands SDK condenser architecture: a `Condensation` event carries `forgotten_event_ids` ("List of event IDs to filter out"), `summary`, and `summary_offset`; `View.from_events()` filters forgotten events and inserts the summary; `LLMSummarizingCondenser` defaults `max_size=120`, `keep_first=4`, condenses to `max_size // 2`. Forgotten events stay in the event log (filtered at view time) but the doc does not describe an agent-facing tool to re-read them. — [OpenHands SDK docs](https://docs.openhands.dev/sdk/arch/condenser)
- OpenHands condenser launch (Calvin Smith, 9 Apr 2025): on a SWE-bench Verified subset the condenser solved 54% vs 53% baseline, with "up to 2x" per-turn API cost reduction; no statement about recalling condensed events. — [OpenHands blog](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents)
- Letta (MemGPT lineage): memory blocks are pinned in-context; the API stores all messages; state is "never lost, even once evicted from the context window"; old messages "are still retrievable via the API (for developers) and retrieval tools (for agents)". The fetched page did not detail `conversation_search`/archival vector search. — [Letta docs](https://docs.letta.com/guides/agents/memory)
- MemGPT paper (arXiv 2310.08560, Packer et al., 12 Oct 2023 / v2 Feb 2024): "virtual context management" inspired by OS hierarchical memory, moving data between fast (context) and slow (external) tiers with interrupts. Secondary sources describe recall storage (searchable DB of all past messages), archival storage (vector store), eviction warnings at 70% capacity and recursive summaries of evicted messages, and DMR accuracy 92.5% (MemGPT) vs 32.1% (fixed-context GPT-4) **[numbers unverified against the paper body]**. — [arXiv 2310.08560](https://arxiv.org/abs/2310.08560); secondary: [emergentmind](https://www.emergentmind.com/topics/memgpt)
- Cognition ("Don't Build Multi-Agents", Walden Yan, 12 Jun 2025): proposes "a new LLM model whose key purpose is to compress a history of actions & conversation into key details, events, and decisions", notes "This is hard to get right", that Cognition has fine-tuned a smaller model for it, and that it "still hits a limit eventually". Summarization, not pointer-based. — [Cognition blog](https://cognition.com/blog/dont-build-multi-agents)
- Claude Code "microcompact": only third-party explainers found; they describe automatic clearing of old tool results (not the conversation) at an unstated/contested threshold and a cache-aware `cache_edits` path. **[unverified; no official changelog entry located]** — [claudelog](https://claudelog.com/faqs/what-is-micro-compact/), [smartscope comparison](https://smartscope.blog/en/blog/claude-code-codex-compact-comparison/)

**Related "gist + lookup" designs**
- ReadAgent (arXiv 2402.09727, Lee, Chen, Furuta, Canny, Fischer; Feb 2024): episode pagination → gist memory (short episodic summaries) → "interactive lookup" where the agent retrieves passages from the original text; extends effective context 3.5–20× on QuALITY, NarrativeQA, QMSum. Lossless original pages are retrievable; retrieval is agent-driven page lookup, not a learned ranker over tool outputs. — [arXiv 2402.09727](https://arxiv.org/abs/2402.09727)
- Recursive Language Models (arXiv 2512.24601, Zhang, Kraska, Khattab; 31 Dec 2025, v2 28 Jan 2026): treats the long prompt as an external environment the model programmatically examines, decomposes and recursively calls itself over; handles inputs "up to two orders of magnitude beyond" the context window. The reproduction "Think, But Don't Overthink" (arXiv 2603.02615) finds depth-2 recursion or RLMs on simple retrieval tasks degrade performance. — [arXiv 2512.24601](https://arxiv.org/abs/2512.24601v1), [arXiv 2603.02615](https://arxiv.org/html/2603.02615v1)
- Context-Folding (arXiv 2510.11967, Sun et al., 13 Oct 2025): agent branches into a sub-trajectory, then folds it, "collapsing the intermediate steps while retaining a concise summary of the outcome"; trained with FoldGRPO; matches/beats ReAct with ~10× smaller active context and "significantly outperforms ... summarization-based context management". The abstract does not say folded steps are recoverable. Follow-ups: FoldAct (arXiv 2512.22733), AgentFold (arXiv 2510.24699). — [arXiv 2510.11967](https://arxiv.org/abs/2510.11967)
- PRO-LONG (arXiv 2607.20064v2, Fox, Wang, Rosu, Dhingra, Duke; 23 Jul 2026): lossless append-only `logs.txt` of every observation/action/outcome; read is programmatic search (grep/regex/Python), no vector index; logs exceeded 320,000 lines in one ARC-AGI-3 game. — [arXiv 2607.20064](https://arxiv.org/html/2607.20064v2)

### Inferences
- jevctx's `expand(pointer)` has at least three direct precedents in 2026 (`recall_event`, `context_recover`, OpenDev read_file-on-path). The novelty claim must therefore rest on **`recall(description)` with a learned reranker over a profile/BM25 shortlist and proactive harness-side recall**, not on byte-exact expansion itself.
- Prior evidence is consistent with jevctx's live finding: when recovery is agent-initiated by ID, models almost never use it (0.54 calls/task even at 32k, ~0 at 128k; zero uses in Franke's central pair). This is the strongest empirical argument for proactive recall.
- No prior pointer system stores a per-output "profile" (type/role/names) or evaluates identifier-free queries.

### Gaps
- Could not read Section 9 of arXiv 2609.00006 for Claude Code tool-result truncation thresholds (page truncated); no official Anthropic source confirms whether Claude Code exposes tool-result references the model can re-expand after compaction.
- The exact placeholder wording Anthropic's API inserts for cleared tool results is not published.
- No source documents JetBrains Junie's or Cognition Devin's context-compaction internals beyond the two blog statements above.

## KQ2. Agent memory papers 2025–2026: retrieval mechanisms, reported numbers, learned rerankers, identifier-removed queries

### Takeaway
Memory systems overwhelmingly retrieve by embedding similarity (Mem0, A-MEM, Memory-R1), knowledge-graph traversal (Zep/Graphiti, AMA-Agent, MemTrace), or programmatic/keyword search (PRO-LONG, AMA-Agent's keyword mode). Learned components exist but are RL-trained memory *managers* or *answer agents* (Memory-R1) or learned *reuse notes* (QCR), not a small decision model reranking a BM25 shortlist. I found no memory paper that evaluates retrieval with identifiers stripped from the query; AMA-Bench comes closest by showing that "similarity-based retrieval is unreliable for machine-generated evidence" and that exact keyword search is needed ~23.5% of the time.

### Cited Findings
- **Memory-R1** (arXiv 2508.19828v5, Yan et al., LMU/TUM et al., Aug 2025): Memory Manager picks ADD/UPDATE/DELETE/NOOP via RL (reward = frozen Answer Agent correctness); Answer Agent retrieves "60 candidate memories ... via similarity-based RAG" (Appendix: top-30 per participant) then applies "memory distillation"; trained on only 152 QA pairs (LoCoMo split 152/81/1,307, adversarial excluded). LoCoMo overall F1 / BLEU-1 / LLM-judge: LLaMA-3.1-8B Memory-R1-GRPO 45.02 / 37.51 / 62.74 vs Mem0 30.41 / 22.22 / 45.68, A-Mem 29.20 / 24.40 / 44.76, LoCoMo RAG baseline 11.41 / 8.71 / 13.62; Qwen-2.5-7B Memory-R1-GRPO 43.14 / 36.44 / 61.51 vs Mem0 30.61 / 23.55 / 53.30, A-Mem 26.08 / 21.78 / 40.78. — [arXiv 2508.19828](https://arxiv.org/html/2508.19828)
- **A-MEM** (arXiv 2502.12110, Xu et al., NeurIPS 2025; v1 17 Feb 2025, v11 8 Oct 2025): Zettelkasten-style notes with contextual descriptions, keywords, tags; "dynamic indexing and linking"; claims "superior improvement" across six foundation models; abstract gives no numbers. — [arXiv 2502.12110](https://arxiv.org/abs/2502.12110)
- **Zep** (arXiv 2501.13956, Rasmussen et al., 20 Jan 2025): Graphiti "temporally-aware knowledge graph engine"; DMR 94.8% vs MemGPT 93.4%; LongMemEval up to +18.5% accuracy and 90% lower latency vs baselines. Retrieval details (BM25/cosine/graph, reranking) not on the abstract page **[unverified]**. — [arXiv 2501.13956](https://arxiv.org/abs/2501.13956)
- **Mem0** vendor-reported: 91.6–92.5 on LoCoMo, 93.4–94.4 on LongMemEval, 64.1 on BEAM at 1M tokens (figures differ across Mem0 pages; eval code on GitHub). — [Mem0 research](https://mem0.ai/research), [memory-benchmarks repo](https://github.com/mem0ai/memory-benchmarks)
- **AMA-Bench** (arXiv 2602.22769v4, Zhao, Yuan, Huang et al., UCSD + Yuandong Tian; ICML 2026): benchmark over agent-environment trajectories (actions/observations/tool outputs). Real-world subset 2,496 QA pairs over ALFWorld, BALROG/LMGame, WebArena, **SWE-bench via OpenHands (~19K tokens, 103 turns avg)**, GAIA via Co-Sight (~289K tokens, up to ~997K), Spider 2.0; synthetic subset 1,200 QA scaling 8K–128K tokens. Capabilities: recall, causal inference, state updating, state abstraction. Results (Qwen3-32B backbone, avg accuracy): AMA-Agent 0.572; EMem 0.461; MemoRAG 0.461; HippoRAG2 0.448; Qwen3-Emb-4B RAG 0.423; MemoryBank 0.340; MemGPT 0.330; A-MEM 0.319; Mem0 0.210; MemAgent 0.277; MEM1 0.123; long-context GPT-5.2 0.723. AMA-Agent retrieval: top-5 by embedding, self-check sufficiency, then graph traversal (~10% of cases) or agent-written keyword/exact-match scripts (~23.5%). Ablations: removing causality graph 0.57→0.43; removing tool-augmented retrieval →0.44. Finding: "Similarity-based retrieval is unreliable for machine-generated evidence" (HippoRAG2 dropped ~43% end-to-end on BabyAI). QA accuracy correlates with end-to-end success (r = 0.96 TextWorld, 0.98 Spider2). — [arXiv 2602.22769](https://arxiv.org/html/2602.22769v4)
- **MemTrace** (arXiv 2610.04838v1, Xu et al., SJTU/MemTensor, 4 Oct 2026): "State-Consistent Memory for Long-Horizon Coding Agents"; immutable Memory Traces bound to repository state; Memory Trace Graph (depend/verify/correct/supersede) + Repository State Graph (defines/calls/imports/covers); when context nears budget, trace bodies are offloaded and only "Memory Anchors" + "Trace Synopses" stay; after refresh the agent rebuilds its frontier and restores only aligned, non-superseded evidence (graph expansion: RSG relations then ≤2 MTG hops). Numbers (Codex CLI): DeepSWE pass@1 56.6 vs 35.4 best baseline; SWE-EVO resolved 69.6 vs 65.2; SWE-Milestone score 46.4 vs 28.6; mini-swe-agent: 66.4/48.7, 63.0/52.2, 48.3/34.5. Backbone deepseek-v4-flash, 200K context, no step limit; DeepSWE runs grouped by native response count into 10–197 / 198–290 / 291–526. 57.0% of file-bound traces later had a bound file modified; P(bound files unchanged) ≈ 0.50 after 1,000 event steps. — [arXiv 2610.04838](https://arxiv.org/html/2610.04838v1)
- **Beyond Retrieval: Query-Conditioned Reuse** (arXiv 2608.12847, Li, Wang et al., XJTU): holds retrieval fixed and varies the *support* given after retrieval; QCR note (workflow invariant, bindings to re-obtain, applicability conditions, verification guardrail) reaches 62.3% avg success over 2,391 WebArena/WorkArena/AppWorld instances, +10.7 pts over full-trajectory injection with 48.9% fewer online tokens; "summary reranking picked a reusable memory for 94.8% of targets". — [arXiv 2608.12847](https://arxiv.org/pdf/2608.12847)
- **Condensation strategies for coding agents** (arXiv 2605.18854v1, Chintalapati et al., 2026): 8 OpenHands condensers on DiscoveryBench (60 tasks, 480 runs, GPT-4o, max 50 iterations). NoOp avg 9.0 events, ~75K tokens. ObservationMasking saved 8.6% tokens; LLMSummarizing cost +23.6%; StructuredSummary +59.0%; LLMAttention +93.9% (LLM condensers were net-negative). Only tasks >10 events showed net savings (ObservationMasking 33.5%). No info-loss metric; slowdowns attributed qualitatively to "losing necessary context and retrying failed approaches". — [arXiv 2605.18854](https://arxiv.org/html/2605.18854)
- Other 2026 memory titles surfaced but not read in full: MINTEval (arXiv 2605.18565, multi-target interference), "Learning What Not to Forget" (arXiv 2606.20954), A-TMA (arXiv 2607.01935), OCR-Memory (arXiv 2604.26622), RRM (arXiv 2607.28156), Memory-R2 (arXiv 2605.21768), "Memory for Autonomous LLM Agents: Mechanisms, Evaluation, and Emerging Frontiers" survey (arXiv 2603.07670). **[contents unverified]**

### Inferences
- The field's retrieval stack for agent memories is embeddings-first with graph/keyword fallbacks; a BM25-shortlist → small-decision-model reranker is not represented in the surveyed papers, so jevctx's reranker is a genuine design gap, especially given AMA-Bench's finding that similarity search fails on machine-generated tool output.
- AMA-Bench's SWE-bench/OpenHands slice (103 turns, 19K tokens) and MemTrace's 291–526-response DeepSWE bucket are the nearest existing testbeds for "recall of past tool outputs in coding".

### Gaps
- No paper found that evaluates memory retrieval with identifiers/named entities removed from the query (jevctx's 69% vs 18% setting appears novel).
- Zep's and Mem0's exact retrieval pipelines (whether they rerank) were not confirmed from primary text.
- MemoryBank, MemAgent, MEM1 mechanisms were only seen as baseline rows in AMA-Bench; their own papers were not fetched.

## KQ3. Long-horizon coding benchmarks: which have 100+-turn sessions where old observations are needed again?

### Takeaway
Few public coding benchmarks routinely produce 100+ turns per episode. Candidates with documented long trajectories: MemTrace's DeepSWE runs (up to 526 responses), AMA-Bench's SWE-bench/OpenHands trajectories (103 turns avg), managed-context runs in the harness-design study (median 50–180 turns at 32k), and multi-task persistent-repo benchmarks (SWE-Milestone, SWE-EVO) where earlier observations matter across milestones. SWE-bench Pro, Terminal-Bench 2, TheAgentCompany and LoCoBench-Agent cap or average well under 100 turns (50-turn caps; 10–40 avg).

### Cited Findings
- **SWE-bench Pro** (arXiv 2509.16941, Deng, Da, Pan et al., Scale AI; v1 21 Sep 2025, v2 14 Nov 2025): 1,865 problems / 41 repos (public 731, commercial 276); reference solutions avg 107.4 LOC across 4.1 files, >100 tasks need >100 lines; evaluation capped at **50 turns**; no average turn counts reported. Scores: public set (SWE-Agent) Claude Sonnet 4.5 43.6%, Sonnet 4 42.7%, GPT-5 high 41.8%; commercial Opus 4.1 17.8%, GPT-5 15.7%. Failure analysis: Claude Sonnet 4's top failure was "context overflow from file listing" 35.6% and "endless file reading" 17.0%. — [arXiv 2509.16941](https://arxiv.org/html/2509.16941v2)
- **Terminal-Bench 2.0** (arXiv 2601.11868, Merrill et al., 17 Jan 2026; ICLR 2026): 89 tasks; frontier agents <65%; no turn statistics on abstract page. A synthetic SFT paper reports 27.4 avg turns per trajectory for its terminal training set (not a benchmark measurement). — [arXiv 2601.11868](https://arxiv.org/abs/2601.11868), [ICLR 2026 page](https://proceedings.iclr.cc/paper_files/paper/2026/hash/444a3737adaee10d86ad2ef5f74468e6-Abstract-Conference.html), [arXiv 2606.03461](https://arxiv.org/pdf/2606.03461)
- **TheAgentCompany** (arXiv 2412.14161v2, 19 May 2025; NeurIPS 2025): 175 tasks; "steps" = LLM calls; best OpenHands+Gemini-2.5-Pro 30.3% success at 27.2 avg steps; range 14.6 (GPT-4o) to 39.9 (Gemini-2.0-Flash). — [arXiv 2412.14161](https://arxiv.org/html/2412.14161v2)
- **LoCoBench-Agent** (arXiv 2511.13998, Salesforce, Nov 2025): 8,000 scenarios / 1,000 projects (2K–41K LOC); context 10K–1M tokens in four tiers; **max 50 turns**, observed 10–22 avg turns; 8 tools incl. `codebase_search` (semantic); 9 metrics incl. **Multi-Session Memory Retention** (0.32–0.37 for all models — "measures whether agents correctly reference variables, functions, and files from earlier turns") and **Long-Range Dependency Resolution**; comprehension vs efficiency r = −0.42. — [arXiv 2511.13998](https://arxiv.org/html/2511.13998v1)
- **SWE-EVO** (arXiv 2512.18470, Thai, Le, Nguyen Manh, Phan, Bui, FPT; Dec 2025): 48 release-sized tasks from 7 Python projects, ~21 files each, avg 874 tests; GPT-5+OpenHands 21% (v1) / gpt-5.2 22.92% vs 72.80% on SWE-bench Verified (v2); introduces **Fix Rate** for partial progress. — [arXiv 2512.18470](https://arxiv.org/abs/2512.18470v1)
- **SWE-Milestone** (arXiv 2603.13428, Deng et al., ICML 2026): milestones linked by a dependency DAG over a persistent repository built by "DeepCommit"; 12 models × 4 frameworks; performance falls from >80% isolated to ≤38% continuous; errors propagate across milestones. — [ICML 2026 proceedings](https://proceedings.mlr.press/v306/deng26d.html), [arXiv 2603.13428](https://arxiv.org/pdf/2603.13428)
- **DeepSWE** (as used by MemTrace): 113 tasks / 91 repos / 5 languages; MemTrace groups runs into 10–197 / 198–290 / **291–526** responses. — [arXiv 2610.04838](https://arxiv.org/html/2610.04838v1)
- **AMA-Bench SE slice**: SWE-bench via OpenHands trajectories ~19K tokens, **103 turns avg**; GAIA/Co-Sight up to ~997K tokens. — [arXiv 2602.22769](https://arxiv.org/html/2602.22769v4)
- **Harness-design study**: at 32k, managed tiers reach median **50–180 turns** on SWE-Bench Verified / Terminal-Bench 2.1; Nemotron-3 550B median SWE-Bench length 70–74 turns depending on context setup. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- **Vending-Bench / Vending-Bench 2** (Andon Labs; arXiv 2502.15840): v2 runs a simulated year; Claude Opus 4.6 $8,017.59 (Feb 2026); the original paper found agents with larger memory performed worse and no correlation between failures and context-window fill. Not a coding benchmark. — [Andon Labs](https://andonlabs.com/evals/vending-bench), [arXiv 2502.15840](https://arxiv.org/pdf/2502.15840)
- **Context rot** (Chroma, Hong, Troynikov, Huber, 14 Jul 2025): 18 models; LongMemEval full prompts ~113K tokens vs focused ~300 tokens, every model better on focused; semantic (low lexical similarity) needles degrade faster; even one distractor reduces performance; 194,480 calls. Motivates removing low-value tool output rather than keeping it. — [Chroma](https://trychroma.com/research/context-rot)
- Nemotron-Cascade 2 allows up to 200 turns with 256K context for SWE-bench Verified (a cap, not an average). — [arXiv 2603.19220](https://arxiv.org/pdf/2603.19220)

### Inferences
- The right live testbeds for jevctx are (i) SWE-Milestone / SWE-EVO (persistent repo, cross-task dependencies, earlier test logs and file reads become relevant again), (ii) DeepSWE-style multi-language tasks with no step cap (MemTrace's 291–526-response bucket), and (iii) any harness run at a deliberately tight budget (32k) where the harness-design study shows management actually changes outcomes.
- SWE-bench Verified at ~25 turns (jevctx's live setting) sits where every prior study found management, recall and offloading to be approximately neutral.

### Gaps
- No benchmark explicitly constructs tasks that *require* re-reading an earlier tool output after it has been dropped; LoCoBench-Agent's Multi-Session Memory Retention is the nearest scored proxy.
- SWE-Lancer, Multi-SWE-bench, MLE-bench, "SWE-bench Long" and "revisit chain" harnesses were not located with turn statistics in this pass.
- SWE-Milestone's turn counts per milestone were not available from the abstract/proceedings pages.

## KQ4. How does prior work measure "the agent later needed something that was dropped"? Established metric names?

### Takeaway
There is no established metric. Prior work measures the symptom indirectly: recall-tool call rate (calls/task), end-task success deltas between elision-only and elision+recall tiers, window-overflow rate, LoCoBench-Agent's "Multi-Session Memory Retention", AMA-Bench's QA accuracy over trajectories (recall/causal/state-update/abstraction), MemTrace's state-memory alignment, PRO-LONG's log-truncation ablation, and QCR's note-vs-trajectory utility. Several papers explicitly state they did not measure retrieval need or recovery quality.

### Cited Findings
- Harness-design study: reports **mean `recall_event` calls per task** (Table 13) and the **T2−T1 accuracy delta (−0.36 pts)** as the evidence that recall adds nothing; also **window-overflow failure rate** (78.7%→8.7% for T0 from 32k→128k) and trajectory-length medians. It does not characterize *what* was recalled. — [arXiv 2609.20804](https://arxiv.org/html/2609.20804)
- Franke 2026: reports archival batch counts, recovery-call counts (0), and byte-exact integrity; states explicitly that "the effect of archiving on decisions and downstream retrieval is unmeasured" and defines no lost-context metric. — [arXiv 2610.10590](https://arxiv.org/html/2610.10590v1)
- Condensation-strategies paper: "no direct metric for information loss or for cases where agents needed dropped context later"; proxies are hypothesis-quality score, completion rate, event count, and a Faster/Same/Slower split vs NoOp (e.g., ObservationMasking 32/27/41%). — [arXiv 2605.18854](https://arxiv.org/html/2605.18854)
- LoCoBench-Agent: **Multi-Session Memory Retention** (0.32–0.37) and **Long-Range Dependency Resolution** (>0.50 high performers, <0.47 low). — [arXiv 2511.13998](https://arxiv.org/html/2511.13998v1)
- AMA-Bench: evaluates retrieval of past observations via QA over trajectories with four capability labels (**recall, causal inference, state updating, state abstraction**), LLM-judge accuracy + F1; validates with correlation to end-to-end success (r = 0.96/0.98). — [arXiv 2602.22769](https://arxiv.org/html/2602.22769v4)
- MemTrace: **state-memory alignment** (57.0% of file-bound traces later invalidated; P(unchanged) ≈ 0.50 after 1,000 steps) and "semantic evidence invalidations"; downstream task outcome is the only direct measure of recovery quality. — [arXiv 2610.04838](https://arxiv.org/html/2610.04838v1)
- PRO-LONG: tool-ladder ablation (read-only log 23.1% → +grep 27.2% → +Python 38.3% → +write 41.2% pass@1, GPT-5.5), **log truncation to last 25 actions** scores below full log with widening gap at best@k, workspace-persistence ablation (0.5 pt vs ~4 pt). — [arXiv 2607.20064](https://arxiv.org/html/2607.20064v2)
- QCR: full-trajectory injection utility falls from +18.4 to +2.9 pts on long traces vs +21.9→+13.2 for the note (third-party restatement of paper figures) **[finer figures unverified]**. — [arXiv 2608.12847](https://arxiv.org/pdf/2608.12847), [agentpatterns summary](https://agentpatterns.ai/context-engineering/query-conditioned-trajectory-reuse/)
- Chroma context-rot uses NIAH accuracy vs input length, with semantic-vs-lexical needle similarity (0.445–0.829) and distractor counts as the independent variables. — [Chroma](https://trychroma.com/research/context-rot)

### Inferences
- A defensible new metric for jevctx would be a *counterfactual-need* measure: fraction of turns where the model's next action references (by path/name/identifier) content that exists only in an elided output, and whether recall surfaced it. Nothing in the surveyed literature names such a metric, so it would be a contribution rather than a replication.
- Reporting recall-call rate and T2−T1-style deltas is the de facto convention; jevctx's "once per 20 runs" is directly comparable to Table 13 of arXiv 2609.20804.

### Gaps
- No paper found that logs *post-hoc* whether a dropped tool output was later re-fetched by re-running the same command (which would be the cheapest need-signal).

## KQ5. Proactive retrieval (harness retrieves for the model before the turn): prior examples

### Takeaway
Harness-side retrieval of *repository* context is standard in commercial coding tools (Cursor's Turbopuffer-backed semantic index, Augment Context Engine, JetBrains Context), but it targets the codebase, not the agent's own past tool outputs. Research systems that retrieve the agent's own history proactively are AMA-Agent (hybrid embedding → graph/keyword, but at QA time), MemTrace (frontier rebuild after context refresh), and Anthropic's "just-in-time" framing, which is agent-initiated. I found no prior system that judges recalled past-observation hits against the *new user message* on the agent's behalf.

### Cited Findings
- Anthropic: just-in-time retrieval = lightweight identifiers loaded at runtime; Claude Code "drops CLAUDE.md files into context up front, then uses glob and grep to fetch other files on demand" (agent-initiated hybrid). — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Cursor: chunks and embeds codebases with its own embedding model into per-codebase Turbopuffer namespaces; Merkle-tree sync; Turbopuffer cites Cursor's figures that semantic search "increased code retention by 2.6% on large codebases and reduced dissatisfied user requests by 2.2%". **[Cursor figures relayed via Turbopuffer, not verified at cursor.com/blog/semsearch]** — [Turbopuffer customer page](https://turbopuffer.com/customers/cursor)
- Augment Code Context Engine MCP (Feb 2026): semantic retrieval layer for any MCP agent; vendor-claimed 70%+ gains across Claude Code/Cursor/Codex, +80% Claude Code / +71% Cursor on 300+ enterprise PRs. **[vendor-reported]** — [Augment blog](https://www.augmentcode.com/blog/context-engine-mcp-now-live)
- JetBrains Context (announced Jul 2026, early access): incremental semantic index of repositories for Junie CLI, Claude Code, Codex CLI; vendor-reported up to 68% fewer agent turns, 59% less latency, 48% lower cost. **[vendor-reported]** — [JetBrains blog](https://blog.jetbrains.com/ai/2026/07/introducing-jetbrains-context-repository-intelligence-for-coding-agents/)
- AMA-Agent: embedding top-5 → sufficiency self-check → graph traversal (~10%) or scripted keyword search (~23.5%); hybrid retrieval over the agent's own trajectory graph. — [arXiv 2602.22769](https://arxiv.org/html/2602.22769v4)
- MemTrace: after a context refresh the harness-side memory system "rebuilds its execution frontier, checks candidate evidence, and restores only what the next action needs" (graph expansion, alignment check). — [arXiv 2610.04838](https://arxiv.org/html/2610.04838v1)
- OpenDev: adapts the recovery hint to the agent's tools (read_file vs delegate to a Code Explorer subagent vs search with offset/limit) — harness-side hinting, not retrieval. — [arXiv 2603.05344](https://arxiv.org/html/2603.05344)
- Claude Code post-compaction: restores up to 5 recently accessed files (`POST_COMPACT_TOKEN_BUDGET = 50 000`) — a fixed recency heuristic, not relevance-judged. — [arXiv 2609.00006](https://arxiv.org/html/2609.00006), [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Memory tool protocol auto-injected by the API: "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" — proactive *prompting* to retrieve, with the agent doing the retrieval. — [Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

### Inferences
- Proactive, relevance-judged recall of the agent's *own* earlier tool outputs (jevctx's "proactive recall") is not described in the surveyed sources; the closest analogues are recency heuristics (Claude Code's 5 files) and state-rebuild after refresh (MemTrace).
- Windsurf and Sourcegraph Cody were not covered in this pass (see Gaps).

### Gaps
- Windsurf and Sourcegraph Cody context-engine details were not retrieved.
- Cursor's primary blog post on semantic search was not fetched; numbers are second-hand.
- "Action memory" (memory of the agent's own edits) has no direct precedent found beyond OpenCode's shadow-git snapshots and Pi's cumulative modified-file lists (both harness state, not retrievable memory).
