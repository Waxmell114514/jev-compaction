# Prompt-cache-aware context management, cost economics of rewriting an agent transcript, and staleness/supersession of tool observations (as of 2026-10-14)

Scope note: all provider pricing below was read from live docs pages on 2026-10-14. Model names on those pages (Claude Fable 5.1, Opus 5.5, GPT-5.6, Gemini 4 Argon, DeepSeek V4) are what the pages show today; they post-date the $3/$0.30 "Sonnet-class" sheet used in the jevctx draft. Anything marked **[unverified]** could not be confirmed from a primary source.

## KQ1. Has anyone already formalized compaction / context editing as a prompt-cache-economics decision?

### Takeaway
Nobody I found states the jevctx break-even inequality (`dropped × turns_left × read_price > rest_of_tail × (write − read)`) or any closed-form rule with a horizon term. The closest prior art is: (a) Anthropic's own context-editing docs, which frame clearing as "worth breaking your prompt cache" and expose `clear_at_least` as the knob (a threshold, not a formula); (b) TokenPilot (EMNLP 2026 Findings) which names the "trade-off between text sparsity and prompt cache continuity" and uses a hit/miss cost model with no write price and no horizon; (c) CliffCompaction (Sep 2026) which states that any edit forces re-prefill from the common prefix and amortizes it over "a long stretch" but gives no equation; (d) several blogs with the generic cache break-even `N* = (w − r)/(1 − r)`. The "append-only, never modify previous observations" rule is Manus (Jul 2025). A fixed `turns_left` prior is not found anywhere; the budget-awareness literature (BAGEN, ICML 2026) estimates remaining budget online and finds agents are poor at it (r = 0.35).

### Cited Findings

**Harness / provider design docs**

- Manus, "Context Engineering for AI Agents: Lessons from Building Manus" (Yichao 'Peak' Ji, 2025-07-18): "the KV-cache hit rate is the single most important metric for a production-stage AI agent"; "cached input tokens cost 0.30 USD/MTok, while uncached ones cost 3 USD/MTok—a 10x difference"; "the average input-to-output token ratio is around 100:1"; rules: "Keep your prompt prefix stable", "Make your context append-only", "Avoid modifying previous actions or observations", "Ensure your serialization is deterministic", "Mark cache breakpoints explicitly when needed"; tools are masked via logits rather than removed because removal invalidates the cache. — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Anthropic, "Effective context engineering for AI agents" (2025-09-29): defines compaction ("taking a conversation nearing the context window limit" and summarizing), calls tool-result clearing "low-hanging superfluous content" ("once a tool has been called deep in the message history, why would the agent need to see the raw result again?"), says it was "most recently launched as a feature on the Claude Developer Platform". The post **does not mention prompt caching or cache invalidation at all**. — [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Anthropic Context editing docs (`clear_tool_uses_20250919`): "Invalidates cached prompt prefixes when content is cleared. To account for this, clear enough tokens to make the cache invalidation worthwhile. Use the `clear_at_least` parameter to ensure a minimum number of tokens is cleared each time. You'll incur cache write costs each time content is cleared, but subsequent requests can reuse the newly cached prefix." `clear_at_least`: "This helps determine if context clearing is worth breaking your prompt cache." Defaults: trigger 100,000 input tokens, keep 3 tool uses, `clear_tool_inputs=false`. Crucially for jevctx's "request only" design: "Context editing is applied server-side before the prompt reaches Claude. Your client application maintains the full, unmodified conversation history. You do not need to sync your client state with the edited version." Thinking: "When thinking blocks are cleared, the cache is invalidated at the point where clearing occurs." — [Claude Platform docs: Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Factory, "Compressing Context" (Theo Luan, 2025-07-21): two thresholds, `T_max` (trigger) and `T_retained` ("drain line"); narrow gaps cause "Frequent prompt cache invalidation as message history is truncated"; they keep "a rolling summary of the information that actually matters" and "summarize only the newly dropped span and merge it into the persisted summary"; "Once key artifacts are summarized away, the agent must re-fetch them." No cost formula. — [factory.com/news/compressing-context](https://factory.com/news/compressing-context)
- Factory, "Evaluating Context Compression for AI Agents": compared against Anthropic's and OpenAI's compaction on >36,000 production messages (overall score 3.70 vs Anthropic 3.44) [secondhand via search summary; not read in full]. — [factory.ai/news/evaluating-compression](https://factory.ai/news/evaluating-compression)
- OpenAI Codex: a Responses API `POST responses/compact` endpoint shipped with GPT-5.1-Codex-Max ("returns a list of items that can be used in place of the previous input to continue the conversation while freeing up the context window" — dkundel, X post). Remote compaction returns an opaque encrypted blob; I found no OpenAI statement about how compaction interacts with prompt caching. — [dkundel on X](https://x.com/dkundel/status/1997065685831503972); [zackees/clud #813](https://github.com/zackees/clud/issues/813); [Daniel Vaughan: Codex compaction architecture (2026-03-31)](https://codex.danielvaughan.com/2026/03/31/codex-cli-context-compaction-architecture/)
- OpenAI prompt caching docs explicitly name compaction as a cache breaker: "If content or a relevant setting changes before a breakpoint, the prefix after that change cannot match the existing cache entry"; extending an earlier message or compaction "can also reduce reuse by changing the prefix." — [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Cognition: I found no primary Cognition/Devin post on compaction-vs-cache; secondary sources only cite the June 2025 "don't build multi-agents" position. Cursor and Augment: no primary source on cache-aware compaction found. **[gap]**

**Claude Code's implementation (reverse-engineered, not official)**

- Claude Code has three mechanisms per issue #42542 (opened 2026-04-02, still open, no Anthropic reply): (1) *time-based microcompact* (`microCompact.ts:422`) — if the gap since the last assistant message exceeds a threshold, old tool results are content-cleared; config `tengu_slate_heron {"enabled": false, "gapThresholdMinutes": 60, "keepRecent": 5}`; (2) *cached microcompact* (`microCompact.ts:305`) — "uses the `cache_edits` API to delete old tool results from the server-side cache"; (3) *session memory compact* keeping ~40k recent tokens. Sentinel string: `[Old tool result content cleared]`. — [anthropics/claude-code #42542](https://github.com/anthropics/claude-code/issues/42542)
- Rationale of the time-based path (Dibia, 2026-04-06, analyzing source shipped 2026-03-31): if enough time has passed "the server-side prompt cache has likely expired", so clear before re-caching — "no point paying to re-cache content the server already forgot." Clears results of Read, Bash, Grep, Glob, WebFetch, Edit, Write. A code comment cites internal "BQ 2026-03-01": "Missing [cache invalidation] made 20% of tengu_prompt_cache_break events" — i.e. 20% of cache breaks were caused by Claude Code's own context management. — [Victor Dibia, "Inside Claude Code"](https://newsletter.victordibia.com/p/inside-claude-code)
- `cache_edits` mechanism (gist, 2026-05-16): "Tool result blocks before the last `cache_control` marker get `cache_reference` fields pointing to the corresponding `tool_use_id`"; "the API can delete specific tool results from the cached prefix without invalidating the entire cache"; "the client sends `cache_edits` blocks that instruct the API to delete specific cache references". — [gist ssskip](https://gist.github.com/ssskip/e0bf6e60f37c3968ae1a3d1434861313). Barazany (2026-03-31) concurs: "When the prompt cache is warm, Claude Code doesn't modify local messages at all" and queues `cache_edits`. — [barazany.dev](https://barazany.dev/blog/claude-codes-compaction-engine)
- **Important caveat**: `cache_edits` / `cache_reference` do **not** appear in the public Context editing docs page I read; a commenter on #42542 says the cached path "is gated out of external builds" and another found 0 microcompact events in 4,700+ intercepted calls. Treat `cache_edits` as an undocumented/internal capability. **[unverified against official docs]**
- Full-compaction cache trick: the summarization call reuses the same system prompt, tools and message prefix and appends the compaction instruction as a new user message — "The server sees the same cache key - and hits it"; a separate summarization prompt produced "A 98% cache miss rate". — [barazany.dev](https://barazany.dev/blog/claude-codes-compaction-engine)
- Resume-related cache regression ("up to 20x cost increase on resumed sessions"; $0.50/h → $5–10/h illustration) attributed to attachment blocks drifting out of `messages[0]`, fingerprint instability, and non-deterministic tool ordering. No methodology given for 20x. — [cnighswonger/claude-code-cache-fix](https://github.com/cnighswonger/claude-code-cache-fix)

**Academic**

- TokenPilot (arXiv:2606.17016, v1 2026-06-15, v2 2026-08-28, EMNLP 2026 Findings; Xu et al., 15 authors): "their unconstrained sequence mutations alter layouts, introducing prefix mismatches and cache invalidation"; "This reveals a critical trade-off between text sparsity and prompt cache continuity." Cost model Eq. 2: `K(C') = α·|C'_hit| + |C'_miss|`, α ≪ 1; monetary Eq. 11: `Cost = |hit|·p_hit + |miss|·p_miss + H_out·p_out`. **No cache-write price, no horizon/remaining-turn term, no invalidation penalty term.** Eviction runs "conservatively in stable batches of B turns rather than at every execution step" (B=3 in §4.5 vs 33 in App. A.4 — internal inconsistency). Baselines: LLMLingua-2, SelectiveContext, Keep-Last-N, Summary, LCM, Pichay, MemoBrain, AgentSwing, MemOS, Vanilla. Backbone GPT-5.4-mini; benchmarks PinchBench (123 tasks) and Claw-Eval General (161). Cost from provider usage fields × price sheet ($0.075/M hit, $0.75/M miss, $4.50/M out). Ablation: "slashes total expenditure from $7.24 to $4.22", cache-miss tokens "from 5.943M to 1.589M". **No number of runs/seeds, no CIs.** — [arXiv abs](https://arxiv.org/abs/2606.17016); [HTML v2](https://arxiv.org/html/2606.17016v2)
- CliffCompaction (arXiv:2609.26779, 2026-09-22; Nguyen, Cho, Chen, Dettmers): "Any modification to the context, including compaction and other context-management approaches, invalidates the existing KV-cache and requires re-prefilling the new context from the common prefix." Uncached tokens are "roughly 5 to 6 times as expensive as cached ones in the models we study (Table 9)." Compaction "occurs only occasionally, so each re-prefill is amortized over a long stretch of full cache reuse." Trigger is a token threshold (45K/32K/16K/8K); **no when-to-compact equation**. Design: "only truncating or dropping content, never rephrasing or rewriting it"; "We never compact a compaction". Cost: App. A.1 "perfect-caching" price-sheet model (prompt shorter than previous ⇒ treated as fully uncached) validated against provider-metered "Real Cost" (Table 8; Kimi within ~1%, GLM higher due to lower hit rate). Models: Kimi K2.5/K2.6/K2.7, GLM 5/5.1/5 Turbo/5.3 Flash/4.7 Flash (abstract also names Opus 4.6/4.7, GPT-5.3 Codex). Benchmarks: SWE-bench Verified, Terminal-Bench 2.0/2.1, KernelBench L3. "±" values in Tables 2–3 but seed count not stated; KernelBench single runs. — [arXiv abs](https://arxiv.org/abs/2609.26779); [HTML](https://arxiv.org/html/2609.26779)
- "Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks" (arXiv:2601.06007, v1 2026-01-09, v2 2026-01-31; Lumer et al.): GPT-5.2, GPT-4o, Claude Sonnet 4.5, Gemini 2.5 Pro; DeepResearch Bench; "over 500 agent sessions with 10,000-token system prompts"; 40 sessions per condition; strategies: full-context, system-prompt-only, exclude-tool-results. "prompt caching reduces API costs by 41-80% and improves time to first token by 13-31%". Per-model cost reduction: GPT-5.2 79.3/81.4/79.6%, Sonnet 4.5 77.8/78.5/78.1%, Gemini 2.5 Pro 38.3/41.4/27.8%, GPT-4o 47.8/45.9/46.8%. Cost: "We calculate cost using token counts reported in API responses" × list prices (Table 3; Claude write $3.75 vs $3.00 input). §5.2: write overhead only recovered if later requests read — **but no break-even formula**. Stats: independent-samples t-tests, α=0.05; no CIs. Internal inconsistency: abstract's 13–31% TTFT vs Table 2's 6% and −2.9% for Gemini. — [arXiv abs](https://arxiv.org/abs/2601.06007); [HTML v2](https://arxiv.org/html/2601.06007v2)
- Other 2025–26 KV-cache-aware agent papers (serving side, not request-shaping): KVFlow (arXiv:2507.07400, workflow-aware prefix caching via agent step graph); ActKV (arXiv:2609.31395, keeps prefix intact so cache grows by appending); CacheScout (arXiv:2608.14624, predicts reuse of cached agent contexts); EfficientAgent (arXiv:2609.33762, 79.2% of host-tier KV chunks evicted before reuse); CacheWise (arXiv:2606.16824). — [KVFlow](https://arxiv.org/abs/2507.07400); [ActKV](https://arxiv.org/html/2609.31395); [CacheScout](https://arxiv.org/html/2608.14624); [EfficientAgent](https://arxiv.org/html/2609.33762)
- "Aborted but Not Forgotten: KV-Cache Retention Breaks Rollback Consistency in Language Agents" (arXiv:2608.15939, 2026-08-16; Zhang & Yang): shows the opposite hazard of transcript editing on self-hosted serving — if the transcript is rewritten but the KV cache is retained, "the model can continue attending to content the application believes it discarded"; retained KV "flips a typed protected effect in 25 of 63 audited cells"; rebuilding the cache "closes every cell". Defines *rollback consistency*. — [arXiv abs](https://arxiv.org/abs/2608.15939)
- The Complexity Trap (arXiv:2508.21433, Lindenbauer et al., JetBrains, NeurIPS 2025 DL4C): observation masking matches LLM summarization at about half the cost in SWE-agent on SWE-bench Verified (e.g., Qwen3-Coder 480B 53.8%→54.8%); hybrid cuts cost a further 7%/11%; masking window needed retuning for OpenHands. Does not model prompt caching. — [arXiv](https://arxiv.org/abs/2508.21433v3); [JetBrains blog (2025-12)](https://blog.jetbrains.com/research/2025/12/efficient-context-management/)

**Generic break-even arithmetic (blogs)**

- Break-even reuse count `N* = (w − r)/(1 − r)` for write multiplier w and read multiplier r; ≈1.28 for Anthropic 5-min (1.25/0.1), ≈2.1 for 1-hour (2.0/0.1). — [chudi.dev](https://chudi.dev/blog/claude-prompt-caching-cost); [dev.to synthorai](https://dev.to/synthorai/prompt-cache-write-cost-when-does-the-125x-premium-pay-2j62). (A skills.sh page claims ~8 reads for 1h; arithmetic says ~2.) — [skills.sh](https://skills.sh/yonatangross/orchestkit/prompt-caching)
- Practitioner anecdote: break-even hit ratios "around 30%". **[anecdotal]** — [finout.io](https://www.finout.io/blog/the-discount-you-now-pay-for-prompt-caching-just-became-a-finops-problem)

**Horizon / turns-left estimation**

- BAGEN: Are LLM Agents Budget-Aware? (arXiv:2606.00198, May 2026): progressive interval estimation of remaining budget at each step; "strong agents do not necessarily have strong budget-awareness" (r = 0.35). — [arXiv PDF](https://arxiv.org/pdf/2606.00198)
- "Towards Budget-Aware Agents: Do LLM Agents Know What They Will Spend?" (ICML 2026): rollout-replay protocol re-querying the agent on every prefix; feasibility prediction, early failure detection, interval calibration. — [ICML 2026](https://icml.cc/virtual/2026/67798)
- Budget-Aware Value Tree (arXiv:2603.12634): uses remaining-resource ratio as a scaling exponent, training-free. — [arXiv](https://arxiv.org/html/2603.12634)

### Inferences
- jevctx's inequality is novel in form (explicit write−read premium on the *remaining uncached tail* vs. read-price savings on *dropped tokens × horizon*), but the components are all public: Anthropic documents the write-cost-on-clear, Manus/OpenAI/CliffCompaction state that edits re-prefill from the edit point, and blogs give the per-block break-even. The paper's claim should be positioned as "first to make the decision rule explicit and horizon-dependent," not "first to notice the trade-off."
- The "request only, stored transcript unchanged" property is exactly what Anthropic's server-side context editing already guarantees ("Your client application maintains the full, unmodified conversation history"), so it is not a differentiator vs. Anthropic's API; it *is* a differentiator vs. Claude Code's local time-based microcompact, which rewrites messages, and vs. summarization-based compaction.
- If Claude Code's internal `cache_edits` / `cache_reference` is real, a provider already supports deleting tool results from a cached prefix without invalidating it — this would undercut jevctx's premise that mid-prefix edits always cost a re-write. It is undocumented publicly, so jevctx can state the premise holds for all *documented* provider APIs.
- A fixed `turns_left` prior is weaker than the literature norm (online budget estimation); the paper should at least report sensitivity of the decision to `turns_left`, and could cite BAGEN to justify not trusting the model's own estimate.
- The "5-6x" uncached/cached ratio in CliffCompaction is for Kimi/GLM; with Anthropic's new 0.025x–0.05x read tiers the ratio is 20–40x, which changes the inequality materially (see KQ2).

- No OpenReview reviews of TokenPilot/CliffCompaction found (CliffCompaction is a Sep 2026 preprint; TokenPilot's EMNLP reviews not public).
- No primary Cursor, Cognition, or Augment statement on cache-aware compaction found.
- Could not verify `cache_edits` in any official Anthropic API reference.

## KQ2. Real provider cache pricing and rules (October 2026) to check the cost model

### Takeaway
Anthropic is the only major provider with an explicit write premium on all models (1.25× 5-min, 2× 1-hour) and read discounts now range 0.1× (older models) down to 0.05× (Opus/Sonnet 5.5) and 0.025× (Fable/Mythos 5.1). OpenAI introduced a 1.25× write charge with GPT-5.6+ (reads 0.1×, 0.05× on GPT-6.1 Sol; earlier models: free writes, 0.25×–0.5× reads). Gemini implicit caching has no write cost and 0.10× reads (0.05× on Gemini 4 Argon); explicit caching adds per-hour storage. DeepSeek: automatic, write at 1.0×, reads ~0.02–0.03× of miss price. No provider documents mid-transcript edit-friendly caching; all are strict prefix-hash caches, and Anthropic/OpenAI both say edits before a breakpoint invalidate everything after. The jevctx $3/$0.30 sheet matches Claude Sonnet 4.5/4.6 base/read exactly and the 1.25× write ($3.75) is correct for 5-min TTL.

### Inferences
- Checking the jevctx inequality on Anthropic's sheet: with `write − read = 1.25 − 0.1 = 1.15` (5-min) or `1.9` (1-hour) and `read = 0.1`, a drop of D tokens pays off iff `D × T > 11.5 × R` (5-min) or `19 × R` (1-hour), where R is the rest-of-tail tokens that get re-written and T is turns_left. On Fable 5.1 (`read = 0.025`, write 1.25) the ratio is `(1.225/0.025) = 49` — rewriting the tail almost never pays. On Sonnet 5.5 (`0.05`) it is 24. The paper's "~10% cost reduction" is therefore highly model-dependent and should be reported as a function of `(write−read)/read`.
- On providers with free cache writes (OpenAI pre-GPT-5.6, Gemini implicit, Grok, Moonshot) the inequality degenerates to "always rewrite when D>0 and the rest-of-tail re-prefill is only charged at the uncached rate" — i.e., the write premium term vanishes but the re-prefill still costs `(1 − read) × R` once; the paper should generalize the formula to `D × T × read > R × (1 − read)` for those providers (a one-time full-price re-prefill, not a premium).
- Anthropic's 20-block lookback and the "consecutive tool_result blocks count as one position" rule matter for a tail-rewrite scheme: a rewrite inside the last 20 positions can still hit an earlier breakpoint's entry if the edited block is after it; jevctx's "frozen prefix + work area" matches this model well.
- No provider documents edit-friendly (non-prefix) caching; the only hint is Claude Code's internal `cache_edits`.

## KQ3. Prior work on staleness / supersession / invalidation of tool observations in agent context

### Takeaway
There is direct, very recent prior art: Concord (arXiv:2610.05281, 2026-10-04, SOSP 2026 AgenticOS workshop) links each observation to its source file, detects changes via SHA-256 content hash, and refreshes/annotates/suppresses stale blocks with no model call — and reports 46.4% fewer tokens than the best non-oracle baseline on a 40-task HotpotQA-derived benchmark. Claude Code's Read tool already suppresses re-reads of unchanged files ("Wasted call — file unchanged since your last Read"), and its Edit tool requires the file "must not have changed on disk since that read." Nobody I found measured the *rate* at which observations go stale in real SWE-bench runs (jevctx's 21% figure would be a new empirical datum). Memory-side staleness is covered by the STALE benchmark (May 2026).

### Cited Findings
- Concord / "When Agent Context Goes Stale: Incoherence in Volatile Agent Context" (Liu, Fang, Qian; arXiv:2610.05281 v1 2026-10-04, v2 2026-10-06; AgenticOS @ SOSP 2026): agents "reuse outdated observations and make incorrect claims about the current workspace state"; "Concord links each observation to its source, detects source changes"; blocks record "the source identifier, observed version, and relevant selector or range"; file adapter uses "the SHA-256 of file contents" and "any write that changes the content hash" triggers reconciliation; policies "refresh the block by re-reading the source, annotate the block with a stale-context warning, suppress it from future prompts, or force the agent to re-read"; small edits patched in place via anchored span relocation, larger drift ⇒ block omitted + refresh notice. Prototype "monitors writes routed through apply_patch" (out-of-band changes unhandled). ConcordBench-Pioneer = 40 HotpotQA-derived tasks with injected mutations. Baselines Naive / Alert / Diff / Oracle; models Claude Sonnet 5, GLM 5.2, DeepSeek V4 Pro; "46.4% fewer tokens than the strongest non-oracle baseline"; run count not stated; **no prompt-cache discussion; staleness frequency in the wild not measured** ("under these constructed conditions"). — [arXiv abs](https://arxiv.org/abs/2610.05281); [HTML v2](https://arxiv.org/html/2610.05281v2)
- Claude Code Read tool freshness (issue #60684, opened 2026-05-19, auto-closed "not planned" 2026-06-19, no maintainer reply): Read returns "Wasted call — file unchanged since your last Read. Refer to that earlier tool_result instead." / "Unchanged since last read"; reporter infers it only tracks the assistant's own Edit/Write/NotebookEdit and misses external disk changes; Edit tool docs say "the file must not have changed on disk since that read." — [anthropics/claude-code #60684](https://github.com/anthropics/claude-code/issues/60684)
- Design-note prior art (btipling/invincible #693): persisted tool results should not be rewritten when files change; require a fresh read at mutate time and remind the model that earlier reads are stale; on compaction keep a files-touched list. — [GitHub issue](https://github.com/btipling/invincible/issues/693)
- Benchmark proposal for stale-read resilience (explicit-edit-benchmark #149): agents read a file, run sed/formatter, then patch against original line numbers; without stale-read detection they "either error out or silently overwrite their own changes." — [GitHub issue](https://github.com/alexshpunt/explicit-edit-benchmark/issues/149)
- "Stale Does Not Mean Unsafe: Guard Precision for Tool-Using LLM Agents under Infrastructure State Races" (arXiv:2609.29522): distinguishes state changes that break a safety condition from harmless ones so commit-time guards don't block every changed-since-read case. — [arXiv](https://arxiv.org/html/2609.29522)
- "Masking Stale Observations Helps Search Agents -- Until It Doesn't" (arXiv:2606.00408, 2026-05-29; Zhang et al., UCSD): "stale" = outside a turn-based retention window (age, not supersession); masking gain vs. no-management accuracy is "an asymmetric inverted-U"; masking is a "token-for-turn trade-off." — [arXiv abs](https://arxiv.org/abs/2606.00408)
- STALE: "Can LLM Agents Know When Their Memories Are No Longer Valid?" (arXiv:2605.06527, 2026-05-07): 400 conflict scenarios / 1,200 queries; "Implicit Conflict" where a later observation invalidates an earlier memory; best model 55.2%; "recognizing an outdated memory does not imply applying the updated belief." CUPMem follow-up updates latent state at write time **[secondhand via Emergent Mind]**. — [arXiv](https://arxiv.org/abs/2605.06527)
- Observation masking as context management (The Complexity Trap, 2508.21433) — masks by recency, not by supersession. — [arXiv](https://arxiv.org/abs/2508.21433v3)
- Aider repo map / SWE-agent file viewer: no source found describing staleness tracking; SWE-agent paper describes the viewer interface only. **[gap]** — [SWE-agent paper](https://arxiv.org/pdf/2405.15793)

### Inferences
- jevctx's three supersession rules (same command rerun, same lines re-read, file edited since) are a strict subset of Concord's mechanism (Concord additionally does in-place patching of small edits and watches content hashes rather than agent actions). jevctx's differentiators are: (i) zero infrastructure (derived from the transcript alone, no file watcher), (ii) applied in a cache-aware rewrite, (iii) measured prevalence (21% of tool-output tokens) on real SWE-bench runs — Concord explicitly does not measure prevalence.
- Because Claude Code's own Read tool already elides unchanged re-reads at the tool layer, "same lines re-read" supersession will be rarer in Claude Code transcripts than in SWE-agent/OpenHands transcripts; the paper should state which harness its 21% comes from.
- Concord must be cited and compared; it was posted 10 days before today's date, so a reviewer will know it.

### Gaps
- No paper found that measures what fraction of tool-output tokens become superseded in real coding-agent runs.
- Could not confirm how Aider's repo map or OpenHands' condensers handle file-change invalidation (no primary source retrieved).

## KQ4. Methodological bar for a cost claim (runs, seeds, paired tests, cost reporting)

### Takeaway
The accepted standard in 2025–26 agent papers is: cost computed from provider-reported usage fields × a stated public price sheet (TokenPilot, Don't-Break-the-Cache, CliffCompaction), with CliffCompaction going further by validating the price-sheet model against provider-metered real cost (~1% on Kimi). On variance, "On Randomness in Agentic Evals" (ICLR 2026 workshop) shows single-run SWE-bench Verified pass@1 moves 2.2–6.0 points run-to-run and σ>1.5 pts even at temperature 0, so one-run-per-arm is below the bar; Nebius uses 5 seeds and reports mean ± error; Miller (Anthropic, 2024) recommends paired standard errors with score correlations, clustered SEs, and power analysis; HAL (ICLR 2026) makes cost-controlled reporting the default. No source explicitly describes paired bootstrap or A/A controls for agent cost comparisons, but Miller's paired-SE recommendation is the closest formal standard.

### Cited Findings
- "On Randomness in Agentic Evals" (Bjarnason, Silva, Monperrus; ICLR 2026 workshop "Agents in the Wild"): 60,000 trajectories on SWE-bench Verified, 3 models × 2 scaffolds; "single-run pass@1 estimates varied by 2.2 to 6.0 percentage points depending on which run was selected"; "Standard deviation at temperature 0: exceeded 1.5 percentage points"; gains of 2–3 points "may reflect evaluation noise"; trajectories "diverge within the first few percent of tokens". Recommendations: multiple independent runs per task; power analysis to choose run count; report pass@k and pass^k with k>1. — [ICLR 2026 page](https://iclr.cc/virtual/2026/10016323); [OpenReview](https://openreview.net/forum?id=UFukKhqCpr)
- Miller, "Adding Error Bars to Evals" (arXiv:2411.00640, 2024-11-01, Anthropic): §4.2 "We therefore recommend using the paired version of the standard error estimate wherever practicable"; "We encourage authors of technical reports to include pairwise differences, pairwise standard errors, and score correlations"; §3.1 resampling K times per question reduces variance (1→2 samples cuts variance by a third in the worked example); §2.2 clustered SEs; §5 power analysis; §2.1 "We suggest reporting the standard error of the mean alongside (beneath) the mean". Companion post: clustered SEs "can be over three times as large as naive standard errors". — [arXiv HTML](https://arxiv.org/html/2411.00640v1); [Anthropic post](https://www.anthropic.com/research/statistical-approach-to-model-evals)
- "Position: Don't Use the CLT in LLM Evals With Fewer Than a Few Hundred Datapoints" (arXiv:2503.01747) — relevant because jevctx has n=28 runs. — [arXiv](https://arxiv.org/pdf/2503.01747)
- Nebius: "we repeat each agent run five times with different seeds and report both mean performance and its estimation error"; used a 50-problem SWE-bench Verified subset to afford repeats. — [Nebius blog](https://nebius.com/blog/posts/training-and-search-for-software-engineering-agents)
- SWE-rebench: reporting only the best of several runs "risks overstating the model's actual capabilities and resolved rate." — [arXiv](https://arxiv.org/pdf/2505.20411)
- AI21: repeating ~500 instances at duplicity 4/8/16 across two variants required ~16k Docker containers in one evaluation window. — [AI21 blog](https://www.ai21.com/blog/scaling-agentic-evaluation-swe-bench/)
- Kapoor et al., "AI Agents That Matter" (2024): "agent evaluations must be cost-controlled"; accuracy-vs-cost Pareto curves. HAL (ICLR 2026): "cost-controlled evaluations by default", tracks token usage without agent code changes; 21,730 rollouts, 9 models × 9 benchmarks, ~$40,000; leaderboard shows per-run $ (e.g., $87.16 top CORE-Bench Hard). — [AI Agents That Matter](https://arxiv.org/html/2407.01502v1); [HAL](https://hal.cs.princeton.edu/)
- How cache-aware papers report cost: TokenPilot — hit/miss counts "gathered directly from the explicit metadata fields returned by the provider APIs" × official GPT-5.4-mini prices; no seeds/CIs. Don't-Break-the-Cache — 40 sessions/condition, usage fields × list prices, independent t-tests, no CIs. CliffCompaction — perfect-cache price-sheet model (Table 9) validated against provider-metered "Real Cost" (Table 8), "±" in tables, seed count unstated, KernelBench single runs. — [TokenPilot](https://arxiv.org/html/2606.17016v2); [DBtC](https://arxiv.org/html/2601.06007v2); [CliffCompaction](https://arxiv.org/html/2609.26779)
- Terminal-agent survey notes a matched SWE-bench Lite comparison where a variant "used more input tokens without an outcome gain" — a cost-only effect in a single run. — [arXiv:2608.20485](https://arxiv.org/pdf/2608.20485)

### Inferences
- jevctx's current evidence (28 runs, hypothetical $3/$0.30 sheet, 16–17% smaller requests, ~10% cost, 93% vs 95% cache-hit share) would meet the *cost-computation* bar if it (a) uses provider-reported `cache_read_input_tokens` / `cache_creation_input_tokens` rather than simulated counts and (b) states the price sheet and shows sensitivity to the read multiplier (0.1 / 0.05 / 0.025). It does **not** meet the *variance* bar: with n=28 and run-to-run σ>1.5 pts on resolve rate, a one-run-per-arm comparison cannot distinguish a 2-point accuracy change from noise, and cost per instance is also heavy-tailed.
- Minimum credible design implied by the sources: ≥3–5 seeds per arm on the same instance set; paired per-instance differences (jevctx is naturally paired since the rewrite is applied to the same trajectory's requests) with paired SE / bootstrap CI; an A/A arm (same config twice) to show the noise floor; report pass@1 mean ± SE and cost mean ± SE; and ideally one arm where real billed cache tokens are compared to the model's predicted tokens (CliffCompaction's Table 8 pattern).
- Because jevctx's rewrite is request-side on a fixed transcript, a *replay* (offline) cost evaluation is deterministic and paired by construction — the variance problem bites only when the rewrite is applied *live* and may change model behavior (accuracy). The paper can separate these: deterministic replay cost (no seeds needed, but must be validated against real metered cost) vs. live accuracy (needs seeds).

### Gaps
- No explicit example found of a paper *rejected* for one-run-per-arm; the critique exists as a position (On Randomness; SWE-rebench) rather than a documented rejection.
- No source found describing A/A controls or paired bootstrap specifically for agent cost comparisons.
- Could not retrieve the full OpenReview reviews for "On Randomness in Agentic Evals".
